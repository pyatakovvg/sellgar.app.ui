# RFC: Операции навигации и ревалидация

- Статус документа: target
- Статус RFC: accepted
- Статус реализации: partial
- Текущий контракт: [навигация и ревалидация](../../README.md#навигация-и-ревалидация), [Collector](../../core/collection/runtime/collector/README.md).

## Назначение

Описать поэтапный внутренний рефакторинг навигации и ревалидации. Реализованы
контекст выполнения, отдельное планирование целей ревалидации и начало новой
выборки Collector при явном повторном входе. Оценка общего executor остаётся
отдельным этапом. Наличие этих внутренних компонентов не означает реализации всей
описанной модели.

## Текущая механика

NavLink, NavItem и программная навигация используют общий core pipeline.
Framework разрешает цель, выполняет blockers и policies, подготавливает
необходимые runtime, фиксирует навигацию и историю, синхронизирует bridge и
запускает запланированную ревалидацию.

Новая ветка загружает данные до commit. Повторный переход к активной ветке
переиспользует экземпляры и обновляет данные после commit. Обычная ошибка
ревалидации сохраняет уже принятую навигацию и прежние loader data.
Восстановление retained activation может происходить без loader.

Исходный запрос содержит явно выбранную цель. Контекст NavigationOperation
сохраняет её и явную причину запуска при передаче в Module loader.
Выбор runtime для очередного revalidate принадлежит планировщику.
Общий navigation.pending не описывает выполнение конкретного владельца:
его ревалидация может совпасть с переходом в другой раздел.

## Предлагаемые границы

1. Описание операции сохраняет её происхождение, исходную цель, идентичность
   и явную связь с породившей операцией. Оно существует во время выполнения
   и не становится второй историей или глобальным mutable current-context.
2. План определяет участие конкретных runtime: подготовку, переиспользование,
   восстановление и ревалидацию. Причина запуска отделена от области выполнения.
3. Исполнение применяет план с существующими гарантиями policies, отмены,
   commit, публикации данных и cleanup.

Контекст относится к конкретному owner scope и выполнению. Class token
недостаточен для различения экземпляров одного модуля. Контекст передаётся
по фактической цепочке вызовов; прямой revalidate не наследует причину
посторонней навигации через глобальное состояние.

## Реализованный Контекст Выполнения

Внутренний `NavigationOperation` принадлежит
`core/router/runtime/navigation-operation`. Он содержит уникальную identity,
исходный NavigationState, источник internal/external, явный trigger и ссылку
на породившую навигацию при policy redirect. Trigger фиксируется в точке
запуска: target, root, query, close, bridge-request, restore, history, session
или recovery. Redirect создаёт новую operation со ссылкой на родительскую.
Контекст не сохраняется в history и не становится глобальным current state.

Application передаёт operation через Router preparation и postcommit
revalidation в Route и Module. `RuntimeExecution` принадлежит
`core/runtime/operation/runtime-execution` и создаётся для конкретного запуска
loader: identity, load/revalidation, фактический RuntimeScope и operation либо
null. Он захватывается существующей LoaderTransaction при постановке в очередь;
пока работает предыдущая транзакция, её контекст не подменяется следующей.
После завершения callback сервис перестаёт выдавать транзакцию как текущую.

Обычный Module revalidate, Widget load/revalidate и Module load без Router
получают собственный execution с navigation: null. Они не наследуют контекст
из Application pending, соседнего scope или текущей навигации. Retained history
restore без loader не создаёт фиктивное выполнение; если history требует
загрузки освобождённой ветки, её loader получает trigger history.

Это внутренние metadata: обязательных полей в ControllerArgs, новых root
exports или аргументов публичных navigation/revalidate hooks нет. Runtime
по-прежнему использует те же очереди, abort, policies и границы публикации.
Collector использует поколение выборки своего владельца, не интерпретируя
навигационные metadata самостоятельно.

External restore описывается только тем, что фактически сообщает существующий
bridge. Дополнительные различия внешних событий не выводятся из совпадения URL
и требуют отдельного решения для bridge contract.

## Реализованное Планирование Ревалидации

`core/router/runtime/navigation-revalidation-planner` владеет чистой функцией
выбора целей. На вход поступают текущая и предыдущая navigation, а также
упорядоченные кандидаты: Router declaration, признак изменения локальной ветки
и конкретная цель. Планировщик не обращается к DI, не запускает providers или
loaders и не хранит состояние между вызовами. Выбранные цели возвращаются
с сохранением ссылок и исходного порядка; они не восстанавливаются по token.

Правила выбора целей:

- отключённая ревалидация не выбирает целей;
- при изменении локальной ветки обновляются сохранённые owners с изменившимся
  query; новые Route уже подготовлены и не загружаются повторно;
- branch выбирает все переданные цели, router — только цели указанного Router;
- restore сравнивает query вдоль общей Router-цепочки. Если query изменились,
  выбираются соответствующие Router scopes; если изменений нет или предыдущая
  navigation отсутствует, выбирается вся переданная ветка.

Существующее сравнение query переиспользуется, включая массивы и вложенные
значения. Навигационный trigger не заменяет эти правила выбора: происхождение
операции и область выполнения остаются разными данными.

RouterRuntime формирует кандидатов из фактического transition plan в прежней
точке: после commit и освобождения заменённой ветки. Затем он выполняет
выбранные providers и Route revalidate с существующими signal, контекстом
операции, обработкой ошибок и параллельностью. Дополнительного исполнения
для сравнения планов в runtime нет.

При одновременной смене query родителя и создании дочерней ветки родитель
ревалидируется после commit. При неизменном query открытие дочерней ветки
не обновляет родителя. Эта поправка выбора целей отделена от initial preload:
уже подготовленные Route не получают повторную загрузку.

## Инварианты

- Сохранить существующее переиспользование runtime, DI-зависимостей,
  контроллеров и providers. Повторный вход не создаёт новые экземпляры.
- Сохранить route identity, params/query, history, retain/release и поведение
  публичных navigation controls.
- Сохранить blockers, canMatch/canActivate, firstAvailable/default resolution,
  redirects и точные exception boundaries.
- Сохранить различие загрузки до commit и ревалидации после commit.
- Не перезапускать initialize/prepare/activate providers при revalidate.
- Сохранить общую и targeted публикацию данных, очереди, abort, supersede,
  session guards, process/error attribution и ожидание cleanup.
- Не выводить намерение обновления из URL, совпадения query или targeted/global.
  Targeted/global определяет область выполнения.

## Collector и повторное открытие раздела

Collector принадлежит framework и может использовать его внутренний контекст,
сохраняя независимость от домена, формы ответа и способа пагинации.

Реализовано начало новой выборки при явной навигации `target`, `root` и
`bridge-request`, включая их redirect-цепочки. После разрешения default/policy
целей планировщик определяет конечную Route и Router. Новое поколение получают
только фактически выбранные для ревалидации Module owners этой цели.
Общие предки и остальные участники branch-ревалидации не сбрасываются.

Решение применяется в существующем postcommit исполнении, после выбора целей
ревалидации и проверки signal. Первый вход остаётся прежней initial load;
`revalidate: false`, неподтверждённые переходы, query/close/history/restore,
самостоятельные recovery/session операции сами по себе не меняют поколение.
Retained activation из истории восстанавливается без нового loader как раньше.

Поколение хранится в owner-scoped LoaderTransactionService и захватывается при
постановке loader в очередь. Старые выполняющиеся, ожидающие и уже полученные,
но не опубликованные результаты не принимаются после смены поколения.
Collector сравнивает поколение транзакции с поколением подтверждённых данных.
Новая выборка начинает callback с пустыми массивом и пользовательским состоянием;
прежние данные остаются до успешной публикации. Ошибка loader/provider сохраняет
их и ожидающую замену, поэтому retry без navigation metadata начинает с начала.
Явный `reset()` потребителя остаётся независимым запросом новой коллекции.

По согласованному изменению публичный метод Collector называется `execute(callback)`;
вызовы и contract fixtures обновлены без изменения поведения. Cursor, offset, форма
ответа и правила завершения остаются ответственностью callback. Module и Widget
используют одинаковую транзакционную механику смены поколения, но навигационный
контекст не распространяется автоматически на Widget owners. Внешний restore
без явного намерения не классифицируется по совпадению URL; дополнительная
семантика bridge требует отдельного контракта.

## Совместимость

Одинаковый адрес не означает одинаковую причину выполнения. FSM публикует
новые snapshots прежнего экрана; Native восстанавливает retained screens;
Next использует ModuleRuntime без нашего навигатора.

Для внешних источников признака external недостаточно. Если bridge port
потребует дополнительного контекста, его совместимость проверяется отдельно.
Не добавлять обязательные поля в существующие публичные контракты без
проверки consumers и facade fixtures.

Сохранить последовательность FSM snapshots и commands, Native history,
presentation completion и cleanup, Next hydration без повторной загрузки.
Перенос внутреннего состояния Collector через SSR snapshot требует отдельного
решения при появлении такого consumer.

## Последовательность рефакторинга

Подготовительные characterization-тесты принадлежат core Application и находятся
в `core/application/lifecycle/application/application-navigation-revalidation.test.ts`.
Они фиксируют порядок первоначальной загрузки и повторного входа, идентичность
runtime и контроллеров, отсутствие повторного initial lifecycle providers,
отключение ревалидации, эквивалентный query, восстановление retained activation,
ошибку после commit и независимую targeted revalidation во время перехода.
Это проверка совместимости текущей механики. Дополнительные assertions
проверяют контекст навигации, redirect parent, изоляцию execution по scope,
очереди и независимость от параллельной навигации. Автоматическое начало новой выборки Collector покрыто отдельными
integration-тестами `application-collector-navigation.test.ts`.

1. Зафиксировать исходные версии, рабочие изменения, различия зеркал и
   существующие ошибки проверок.
2. Дополнить characterization-тесты переходов, истории, идентичности объектов,
   числа загрузок, обязательного порядка стадий и cleanup. Не закреплять
   случайный порядок независимых параллельных операций.
3. Провести внутренний контекст операции в режиме наблюдения, сохраняя
   публичные вызовы и текущее поведение.
4. Отделить планирование ревалидации, сначала сохранив условия выбора целей
   и существующую точку исполнения. Сравнивать планы без двойного выполнения
   запросов.
5. Отдельно оценить общий executor Module и Widget. Сохранить различия
   initial load, pending commit, props snapshots, hydration и ошибок владельца.
   Полное слияние runtime не является обязательной частью предложения.
6. Подключён Collector к подтверждённому контексту владельца; проверяются
   повторное открытие раздела, дозагрузку, завершение и retry.
7. Проверить все потребители и adapters, затем публиковать изменения
   отдельными обратимыми commits.

## Проверки

Покрыть первый вход, reentry с query и без него, NavLink/NavItem/to/root,
вложенные open/close, смену params, retain/release, историю и внешние источники.
Проверить одновременные навигацию и revalidate, reset во время запроса,
completed → reentry, ошибки соседних loader/providers и поздние результаты.

Проверить независимые collectors, одинаковые tokens в разных scopes, Widget
в Module и несколько приложений в одном JS-процессе. Отдельно проверить
revalidate:false, same-query no-op, повторный FSM snapshot и Next hydration.

Внешний переход, одновременно меняющий query родителя и создающий дочернюю
ветку, обновляет сохранённого родителя без повторного initial load дочернего
Module. Отключённая ревалидация сохраняет только location/history commit.

Приёмка включает framework tests, facade typecheck, сборки и smoke потребителей,
Native-проверку на устройстве и проверку удержания памяти. Ускорение или
уменьшение памяти не предполагаются автоматически из-за разделения кода.
